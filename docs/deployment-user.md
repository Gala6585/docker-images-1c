## 3. Подготовка поставки

Разместите файл в назначенной папке:

```text
<сетевая папка>/<DEVELOPER_NAME>/<CONFIG_NAME>/
```

Поддерживаемые типы:

- `.cf` — конфигурация;
- `.cfe` — расширение конфигурации;
- `.epf` — внешняя обработка;
- `.erf` — внешний отчёт.

Рекомендации:

- перед копированием убедитесь, что выгрузка завершена;
- не меняйте расширение файла;
- не размещайте временные и резервные копии с поддерживаемыми расширениями в той
  же папке, если их не нужно анализировать;
- используйте согласованное имя файла;
- не храните рядом текстовые файлы с паролями.

## 4. Запуск проверки из GitLab

1. Откройте проект в GitLab.
2. Перейдите в **Build → Pipelines**.
3. Нажмите **New pipeline** или **Run pipeline**.
4. Выберите нужную ветку.
5. Добавьте переменные запуска:

```text
DEVELOPER_NAME=<имя вашей папки>
CONFIG_NAME=<имя конфигурации>
```

6. Запустите pipeline.

При запуске из GitLab UI переменная `CI_PIPELINE_SOURCE` автоматически получает
значение `web`. Переменную `RUN_SOURCE=rundeck` пользователь вручную не задаёт:
она предназначена для автоматического запуска из Rundeck.

## 5. Этапы pipeline

### 5.1. `unpack_job`

Job находит файлы в сетевой папке, копирует их и извлекает `.bsl`.

Успешный результат означает:

- путь к папке указан правильно;
- поставка доступна Runner;
- `v8unpack` смог обработать файл;
- изменения сохранены в Git и artifacts.

### 5.2. `sonar-analysis`

Job отправляет каталог `unpacked/` в SonarQube.

В SonarQube смотрите:

- статус Quality Gate;
- Bugs;
- Vulnerabilities;
- Code Smells;
- список файлов и строк с замечаниями.

Если Quality Gate не пройден и pipeline настроен последовательно, Vanessa может не
запуститься. Сначала устраните замечания либо согласуйте исключение с ответственным.

### 5.3. `vanessa_tests`

Job запускает feature-сценарии на выделенной тестовой базе.

В GitLab artifacts сохраняются:

- `vanessa-logs/` — технические логи и диагностические снимки;
- `allure-results/` — исходные результаты тестов;
- `allure-report/` — локальный HTML-отчёт, если он включён.

### 5.4. `publish_allure`

Job отправляет `allure-results` на Allure Server и выводит ссылку на готовый отчёт.
Один pipeline обычно формирует один отчёт, внутри которого находятся все
выполненные сценарии.

## 6. Просмотр результата SonarQube

1. Откройте ссылку проекта SonarQube.
2. Проверьте Quality Gate.
3. Откройте список новых замечаний.
4. Отфильтруйте замечания по файлу, типу и критичности.
5. Исправьте исходный объект 1С, сформируйте новую поставку и повторите pipeline.

SonarQube анализирует распакованный BSL-код, а не бинарный `.cf`. Поэтому замечание
нужно сопоставлять с исходным модулем объекта конфигурации.

## 7. Просмотр результата Allure

1. Откройте job `publish_allure`.
2. Найдите строку `Allure report:`.
3. Перейдите по ссылке.
4. Откройте раздел **Suites** или **Behaviors**.
5. Выберите сценарий.
6. При ошибке изучите упавший шаг, сообщение, вложения и скриншот.

Статусы сценариев:

| Статус | Значение |
|---|---|
| `passed` | Сценарий выполнен успешно |
| `failed` | Проверка ожидаемого поведения не прошла |
| `broken` | Сценарий не смог корректно выполниться из-за технической ошибки |
| `skipped` | Сценарий или шаг пропущен |
| `unknown` | Результат сформирован некорректно или неполно |

Несколько тестов в одном Allure-отчёте — нормальное поведение: один pipeline
соответствует одному общему отчёту.

## 8. Добавление новых тестов Vanessa

Feature-файлы добавляются в Git-репозиторий, а не в сетевую папку поставок:

```text
features/<имя теста>.feature
```

Русскоязычный файл должен начинаться примерно так:

```gherkin
# language: ru

Функционал: Проверка документа

Сценарий: Создание документа
    Дано ...
```

Требования:

- расширение строго `.feature`, не `.feature.txt`;
- кодировка UTF-8;
- имя профиля TestClient в сценарии должно точно совпадать с настроенным профилем;
- секреты и пароли нельзя записывать в feature-файл;
- сначала рекомендуется проверить новый сценарий отдельно, затем включить его в
  общий набор.

Добавление через Git:

```bash
git add features
git commit -m "Add Vanessa smoke tests"
git push
```

## 9. Статусы Vanessa

Если используется `vanessa-logs/status.log`, число означает:

| Код | Значение |
|---|---|
| `0` | Ошибок выполнения сценариев нет |
| `1` | В сценариях были ошибки |
| `2` | Ошибка контекста, TestClient или сетевого взаимодействия |
| `3` | Не найдено ни одного сценария для выполнения |
| `4` | Не удалось тихо установить внешнюю компоненту |

Код контейнера `124` не является статусом Vanessa: это превышение заданного
времени выполнения.

## 10. Что проверить при ошибке

| Сообщение или симптом | Действие пользователя |
|---|---|
| Поставка не найдена | Проверить `DEVELOPER_NAME`, `CONFIG_NAME`, имя и расширение файла |
| Нет `.bsl` после распаковки | Убедиться, что поставка не повреждена; обратиться к администратору |
| Sonar Quality Gate failed | Открыть замечания SonarQube и исправить код |
| `Database is locked` | Сообщить администратору 1С; не перезапускать pipeline многократно |
| Профиль TestClient не найден | Сообщить точное имя профиля и ссылку на job администратору |
| Vanessa status `1` | Открыть упавший сценарий в Allure и проверить шаг |
| Vanessa status `2` | Проверить сообщение и передать администратору ссылку на job |
| Vanessa status `3` | Проверить наличие и кодировку feature-файлов, затем фильтры запуска |
| Code `124` | Проверить последний скриншот и сообщить о возможном модальном окне |
| `publish_allure` не создал отчёт | Проверить, создала ли Vanessa файлы `*-result.json` |

## 11. Что приложить к обращению администратору

Передайте:

- ссылку на pipeline и упавшую job;
- имя ветки;
- `DEVELOPER_NAME` и `CONFIG_NAME`;
- имя файла поставки без его содержимого;
- название упавшего feature-сценария;
- время запуска;
- текст ошибки без паролей и строки подключения;
- при наличии — диагностический скриншот из artifacts.

Не пересылайте пароль тестовой базы, содержимое `VA_TEST_CLIENTS_FILE`, токены или
полную строку подключения.
